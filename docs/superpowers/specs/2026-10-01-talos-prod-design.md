# Talos Prod Cluster — Design

Roadmap sub-project 2 ([roadmap](2026-09-26-homelab-roadmap-design.md),
[ADR 0012](../../decisions/0012-hub-and-spoke-topology.md)): build the prod
Kubernetes cluster on Talos, from nothing, in `terraform/environments/prod`.
One control plane and two workers, brought up by one `terraform apply` from
the operator's workstation. Done when `kubectl get nodes` shows three Ready
nodes.

## Problem

`terraform/environments/prod` and `talos/` are unusable in their current
state:

- The prod root pins `telmate/proxmox` `3.0.2-rc04` and Terraform `~> 1.13.0`;
  `modules/talos-vm` pins `3.0.2-rc10` and `~> 1.16.0`. Prod cannot
  `terraform init`.
- The `talos-tp` template and `Talos-K8s` pool are assumed and documented
  nowhere.
- The root also declares four LXC modules (`tk_nas`, `pi_hole`, `traefik`,
  `homepage`) that the LAN services in `shared` replaced.
- Talos machine configs were generated by hand with `talosctl`, with their
  secrets in files under `talos/`.

## Decisions

| Question | Decision |
| --- | --- |
| Existing scaffolding | Deleted, not extended: `modules/talos-k8s`, `modules/talos-vm`, `talos/`, and the prod root's `main.tf`, `outputs.tf`, `prod.tfvars.example` |
| CLAUDE.md's "do not extend prod or `talos/`" rule | Removed in the first commit. It guarded unusable scaffolding; with real work starting it has no purpose |
| Config generation | The `siderolabs/talos` Terraform provider generates secrets and machine configs, applies them, bootstraps and fetches the kubeconfig |
| Where the secrets live | `terraform.tfstate` (local, gitignored) and nowhere else. Never a file in the repo |
| Node image | Image Factory `nocloud` disk image with the `qemu-guest-agent` extension, imported by hand into `talos-tp` |
| Addressing | Static cloud-init `ipconfig0` per clone; Talos reads it at boot. Addresses live in `prod.tfvars` |
| Topology | One control plane, two workers, no VIP |
| Sizes | Start small: 2G control plane, 2 × 2G workers (6G). Grow by editing tfvars |
| Proxmox host automation | A script for the bare-metal steps is a separate follow-up PR |

### Why the Terraform provider

One `terraform apply` goes from blank clones to a kubeconfig, and the
secrets are in a file this repository already treats as sensitive: the state
holds the Proxmox API token today. The alternatives were `talosctl gen config`
with SOPS-encrypted files committed, which adds
a key to manage and a manual `apply-config` and `bootstrap` per node, and
`talosctl` with local gitignored output, which has the same manual steps and
a second place to lose secrets.

The cost: losing the state loses the cluster's PKI, so the cluster is
rebuilt. That is what `docs/rebuild.md` already does for every other
environment after an SSD swap.

### Why `nocloud` with cloud-init

Proxmox's cloud-init drive plus Talos's `nocloud` platform gives each clone
its planned static address on first boot, the same mechanism the Ubuntu VMs
use. The `talos` provider then applies configs to addresses it already
knows. The `metal` image with DHCP would boot into the pool (`.2–.99`) and
need the temporary address discovered before the config could move the node.

## Memory budget

Measured on `pve` 2026-10-01: 31G total, 6.5G available, every VM's host
RSS equal to its allocation (`claude-code` 8G, `nfs-01` 2G, `vault-02` 2G,
dev 4G + 3G + 3G). The roadmap's 10G for prod does not fit.

Prod starts at 2G control plane + 2 × 2G workers = 6G, leaving about 0.5G
and leaning on swap. The sizes are `memory` values in the `talos_nodes`
map, so growing them is a tfvars change and one rolling reboot per node.
Talos's documented minimum is 2G. Watch the control plane's memory once etcd
and the API server are up.

Shrinking `claude-code` (8G, of which `free` showed 1.5G used on 2026-10-01)
would free about 4G and is the first lever if 2G nodes prove too small. It
reboots the VM agent sessions run on, so it is not part of this PR; the
roadmap's sub-project 4 still owns it.

Disk: three 20G disks allocated from the `local-lvm` thin pool; keep its
`data%` in mind.

## Design

### Pins

`environments/prod/versions.tf` matches `shared`: Terraform `~> 1.16.0`,
`telmate/proxmox` `3.0.2-rc10`. It adds `siderolabs/talos`, pinned to an
exact version chosen when the plan is written. The CI `terraform` job's
`for env in dev shared` loops (`init`/`validate` and `tflint`) gain `prod`.

### Module `modules/talos-node`

One VM: a full clone of `talos-tp` in the `Talos-K8s` pool, static
`ipconfig0`, `agent = 1`, inputs for vmid, name, memory, cores, disk size and
address. No resources beyond the VM.

### Prod root

`main.tf` calls the module with `for_each` over `var.talos_nodes`:

```hcl
talos_nodes = {
  cp1 = { role = "controlplane", vmid = 3101, ip = "10.0.0.110", memory = 2048 }
  w1  = { role = "worker",       vmid = 3201, ip = "10.0.0.111", memory = 2048 }
  w2  = { role = "worker",       vmid = 3202, ip = "10.0.0.112", memory = 2048 }
}
```

Addresses and vmids sit in the gitignored `prod.tfvars`;
`prod.tfvars.example` carries placeholders from the `.110–.119` block the
README diagram plans, outside the DHCP pool.

`talos.tf` holds the cluster:

- `talos_machine_secrets`
- `talos_machine_configuration` data sources for the controlplane and
  worker roles, with config patches for hostname and install disk
- `talos_machine_configuration_apply` per node, against its static address
- `talos_machine_bootstrap` on the control plane
- `talos_cluster_kubeconfig`

The cluster endpoint is `https://<cp-ip>:6443`. The Talos and Kubernetes
versions are variables; the Talos version must match the image in
`talos-tp`.

### Secrets handling

`kubeconfig` and `talosconfig` are `sensitive` outputs. Nothing writes them
to disk (no `local_file`). The operator fetches them:

```bash
terraform output -raw kubeconfig > ~/.kube/talos-prod
```

The only files that carry secrets are `terraform.tfstate` and
`prod.tfvars`. The plan verifies each is ignored with `git check-ignore -v`.

### Removed from prod

The four LXC modules, their variables and outputs, and the Debian and
TurnKey template variables.

## Operator steps (in `docs/rebuild.md`)

Done by hand on `pve`, documented in a "Talos prod prerequisites" section
that replaces the old note saying `talos-tp` can be ignored:

1. **Pool and ACL.** Create `Talos-K8s`, then grant `terraform@pve` the
   `TerraformProv` role on `/pool/Talos-K8s`. Without the per-pool ACL,
   placement fails.
2. **`talos-tp` template.** Request a schematic from Image Factory
   (`nocloud`, `qemu-guest-agent`, the pinned Talos version), download the
   disk image, `qm create`, `qm importdisk`, attach the disk, add a
   cloud-init drive and serial console, `agent=1`, `qm template`.
3. **Bring-up.** `terraform apply -var-file=prod.tfvars` from the operator's workstation,
   `terraform output -raw kubeconfig`, `kubectl get nodes`.
4. **Caveats.** The state holds the PKI, so a lost state rebuilds the
   cluster. Resizing a node reboots it; do one at a time.

These steps are written as plain commands so a follow-up PR can turn them
into a host bootstrap script without rewriting them.

## Pull request shape

One draft PR, opened as soon as this spec is committed so the design is
reviewable first. Commits, in order:

1. `docs:` this spec
2. `docs:` remove the scaffolding rule from CLAUDE.md
3. `chore:` delete the old Talos modules, `talos/` and the old prod files
4. `feat:` the `talos-node` module, the prod root and the tfvars example
5. `ci:` add `prod` to the Terraform loops
6. `docs:` `rebuild.md`, README, ADR 0021

The Glance session edits the same README table, diagram, `rebuild.md` and
probably CLAUDE.md; whichever PR merges second merges `main` in and resolves
the conflicts. Bring-up applies stay off the day of Glance's router DNS
cutover.

## Verification

CI runs `validate` and `tflint` on prod, which proves it inits and parses,
nothing more. `terraform plan` is not in CI, and this PR has no state to plan
against. The real check is the operator's apply: the PR description lists the
command sequence, and the cluster is done when `kubectl get nodes` shows
three Ready nodes. No renames are at risk yet because prod has never been
applied; after the first apply, every rename needs a `moved` block
([ADR 0013](../../decisions/0013-terraform-renames-need-moved-blocks.md)).
