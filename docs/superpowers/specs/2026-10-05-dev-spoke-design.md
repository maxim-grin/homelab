# Dev as a Spoke — Design

Roadmap sub-project 4 ([2026-09-26](2026-09-26-homelab-roadmap-design.md)).
The prod hub ([2026-10-03](2026-10-03-prod-platform-hub-design.md)) is
rolled out and verified, and prod's apps are uniform and generated by one
ApplicationSet ([2026-10-06](2026-10-06-uniform-apps-design.md), ADR 0026).
This points that set at dev, retires dev's own ArgoCD, and makes dev safe
to rebuild from scratch at any time.

_Revised 2026-10-09 after the uniform-apps migration: everything prod-only
moved there, and the cutover changed from delete-and-recreate to adopting
dev's live resources in place._

## Problem

Dev still runs as a standalone cluster:

- its own ArgoCD (`dev-argocd.mgryn.cc`), watching `argocd/environments/dev`
- hand-rolled monitoring manifests, not the chart prod uses
- Helm values directories (`cert-manager`, `ingress-nginx`) and Applications
  instead of the uniform `argocd/apps/<dir>/dev` kustomize shape
- VMs named `ubuntu-k8s-master-01` and `ubuntu-k8s-worker-01`, not the
  `<distro>-<env>-<role>` pattern prod uses
- one piece of state git does not hold: jobboard's Postgres, on an
  `nfs-dev` PVC that is deleted with the PVC

The goal is the roadmap's: one ArgoCD showing both clusters, and a dev
that rebuilds with one Terraform apply, one bootstrap playbook and one
registration playbook, after which prod syncs everything else.

## Already done (uniform-apps, #102 and the rollouts)

Not part of this series; the plan only checks them:

- Prod's `apps` ApplicationSet, generating `<cluster>-<dir>` from
  `argocd/apps/*/config.yaml` for clusters labelled `env`.
- The `prod` cluster Secret, AppProject destinations by cluster name, the
  AVP-rendering CMP sidecar, and controller policy `create-update`.
- The hub's Vault policy reading `kv-dev/` (`extra_kv_mounts`).
- Prod's Prometheus receiver at `prometheus.mgryn.cc/api/v1/write` (TLS,
  basic auth), credentials in `kv-prod` and `kv-dev`.
- `scripts/check-appsets.sh` and its tests; the runbooks for rolling an
  app into, and retiring one from, the set.

## Decisions

| Question | Decision |
| --- | --- |
| Dev distribution | Stays kubeadm on Ubuntu. Talos for dev is not ruled out later; not now |
| Shape | Two PR series: A converts dev to a spoke in place, B rebuilds and renames it |
| Application naming | The existing set; dev's apps are `dev-<dir>`: `dev-cert-manager`, `dev-cert-manager-issuers`, `dev-ingress-nginx`, `dev-nfs-provisioner`, `dev-jobboard`, `dev-monitoring-secrets`, `dev-kube-prometheus-stack` |
| Dev app layout | Uniform: `argocd/apps/<dir>/dev` kustomize dirs and an `- env: dev` entry in the app's `config.yaml`. Dev's Helm values dirs become `helmCharts:` kustomizations |
| Registering dev | Declarative cluster Secret labelled `env=dev`, token in Vault, written by an Ansible play. Its own Application `clusters-dev` with the AVP plugin, so prod's plain `clusters` Application never depends on Vault |
| Dev monitoring | Prometheus Operator in agent mode (`kube-prometheus-stack/dev`), remote-writing to prod's receiver |
| Cutover | **Adopt in place.** Dev's Applications drop their finalizers in git, dev's controller is stopped, the hub's `dev-*` Applications take over the live resources, then dev's ArgoCD is uninstalled without cascade. Nothing is recreated and jobboard stays up with its database |
| The one exception | Dev's hand-rolled monitoring has no chart counterpart; it is torn down and the agent-mode install created fresh. Dev's monitoring data is purgeable |
| jobboard data | One dump to the workstation before anything else, as insurance and as sub-5's restore source. The in-place cutover does not need it, but a rebuild or a mistake would |
| Dev afterwards | Holds no state worth keeping once sub-5 moves the DB, so it is rebuildable at any time |

## Prerequisite: the dump

Before any step that touches dev's Applications, the jobboard database is
dumped off the cluster.

- `tools/db-backup.sh dump` (job-board PR #35) against dev, to the
  operator's workstation, never to `nfs-01`.
- The file is validated: it is non-empty and `pg_restore --list` reads it.
- A second copy goes somewhere off the workstation. It is the only copy
  of that data outside the cluster.
- Sub-5 restores it into prod's Postgres.

## Series A: dev becomes a spoke

Dev's VMs stay as they are throughout.

**A1, register dev.**

- A playbook creates the `argocd-manager` ServiceAccount and token on dev
  and writes `server`, `bearerToken` and `caData` to
  `kv-prod/argocd/clusters/dev`. Re-running it after a rebuild
  reconnects the hub.
- A committed cluster Secret `cluster-dev` (`env=dev`, `name: dev`) in
  `argocd/apps/clusters/dev/` carries AVP placeholders for them. The
  `clusters-dev` Application renders it through the AVP plugin.
- `check-appsets.sh` reads the Secret's `server` field; it must tolerate a
  placeholder there.
- ADR 0027 records the decision: dev is a spoke, adopted in place.

**A2, drop dev's finalizers.** As #107 did for prod: remove `finalizers:`
from every Application file under `argocd/environments/dev/applications`,
because dev's `root-dev` selfHeal would restore a hand-patched finalizer.
Nothing else changes. Without finalizers, deleting an Application leaves
its resources alone.

**A3, adopt dev's apps.**

- `cert-manager/dev` and `ingress-nginx/dev` become kustomizations with
  `helmCharts:` (same chart version, same `values.yaml`, `releaseName` and
  namespace pinned to the old release's). The rendered resource names and
  selector labels equal the old Helm render; a DaemonSet selector is
  immutable.
- `config.yaml` gets an `- env: dev` entry for `cert-manager`,
  `cert-manager-issuers`, `ingress-nginx` and `nfs-provisioner`;
  `jobboard` gets a `config.yaml` holding only its dev entry
  (`serverSideApply: true`, carried over from the old Application).
- Dev's Application files for those apps and `app-of-apps`,
  `argocd-config` go from git, with `ansible/playbooks/argocd-dev.yaml`
  and the dev ArgoCD ingress.
- Cutover, as a runbook entry: stop dev's application controller, merge,
  the hub's `dev-*` Applications adopt (the tracking-id moves, as on
  prod), verify nothing was recreated, then uninstall dev's ArgoCD
  without cascade. Merging with dev's controller still running makes two
  ArgoCDs fight over the tracking annotation.

**A4, dev monitoring.**

- `kube-prometheus-stack/dev`: Prometheus in agent mode, no Grafana or
  Alertmanager, node-exporter and kube-state-metrics on, external label
  `cluster=dev`, remote-write to `https://prometheus.mgryn.cc/api/v1/write`
  with credentials from `kv-dev/monitoring/remote-write`. `monitoring-secrets/dev`
  owns the namespace and the credentials Secret, as on prod.
- Dev's hand-rolled `monitoring/{base,dev}` directories go in A4. Its
  `monitoring` Application file is already deleted from git in A3 (with
  the rest of `argocd/environments/dev`), and dev's ArgoCD is uninstalled
  without cascade, so the live workload runs on, orphaned, until A4. The
  order still matters: the operator deletes the `monitoring` namespace on
  dev first, then the PR merges and the hub creates the new pair. The dev entries for the two new apps land in this PR, not A3, so
  the set cannot create them while the old namespace still exists.
- The owner's `/etc/hosts` lines for dev's Prometheus and Grafana go;
  `prometheus.mgryn.cc` is the hub's receiver.

## Series B: rebuild and rename

**B1, new VMs.**

- `terraform/environments/dev` creates `kubeadm-dev-cp1` and
  `kubeadm-dev-w1`, 3G each, with new vmids. The old VMs are destroyed in
  a separate step once the new ones are verified. Creating fresh avoids an
  in-place rename, which would need `moved` blocks (ADR 0013) and would
  leave the Proxmox name, the hostname and the kubeadm node name
  disagreeing.
- The existing kubeadm roles bootstrap the cluster, including the CoreDNS
  hosts play for `vault.mgryn.cc`. Vault's `kubernetes-dev` auth is not
  recreated: AVP runs on the hub and reads `kv-dev` through prod's auth, so
  no dev workload authenticates to Vault (the role's
  `vault_configure_k8s_auth=false` skips it).
- Re-running A1's registration playbook reconnects the hub, and the `dev-*`
  Applications restore every app. They all start at once (generated apps
  have no sync waves); the set's retry carries cert-manager's issuers past
  the CRDs, and a manual sync is the fallback.
- Old `nfs-dev` PVC directories stay on `nfs-01` until the post-sub-5 SSD
  rebuild.

**B2, the proof and the docs.**

- A runbook entry "rebuild dev": the commands in order, a check after
  each, and what the first real run caught.
- `docs/rebuild.md` gets the dev flow.

## Verification

CI covers the manifests, not the cluster: `scripts/check-appsets.sh` (with
`scripts/tests/check-appsets.test.sh`), `check-manifests.sh` and
`check-runbooks.sh` run on every PR. Nothing in CI proves a workload
serves traffic, so each step is also checked on the thing itself.

- After A1: `argocd cluster list` lists dev as Unknown ("no applications" is expected; Successful comes after A3); the hub controller's
  memory stays well under its limit with dev cached (prod cp1 has 4 GiB,
  and sat at its ceiling at 2 GiB).
- After A3: every `dev-*` Application Synced and Healthy; pod ages and the
  jobboard Postgres PVC unchanged (nothing recreated); row counts in
  jobboard's DB equal before and after; the jobboard Ingress answers with
  the right `Host:` header.
- After A4: series with `cluster=dev` appear in prod's Prometheus.
- After B1: nodes Ready, and ArgoCD reconnects without manual edits.

### Automated checks this series adds

The render check already exists (`scripts/check-appsets.sh`); A1 extends it
to the dev Secret. Two more are new; the first runs in CI, the second needs
the live cluster.

- **`terraform test` with mock providers** for `environments/dev`, the
  pattern `environments/prod/prod.tftest.hcl` already uses. It asserts VM
  names, sizes and vmids, and that no resource is replaced under the old
  addresses. CI runs `validate`, not `plan`, so today nothing catches a
  missing `moved` block or an accidental destroy.
- **`scripts/verify-dev.sh`**, a post-apply smoke script. It runs the
  After-A1, After-A3, After-A4 and After-B1 checks as one command:
  `argocd cluster list`, every `dev-*` Application Synced and Healthy, a
  `curl` with the jobboard `Host:` header, and a `cluster=dev` series in
  prod's Prometheus. The "rebuild dev" runbook ends with it, so a rebuild
  proves itself. It is not CI, and it prints `vault status` first, since a
  sealed Vault reads as healthy.

CLAUDE.md's "Verifying, with no test suite" section lists the new checks
in the same PR that adds them.

## Risks

- **Two ArgoCDs fight over a resource** if dev's controller runs while the
  hub adopts. Stop it first; the runbook gates on it.
- **A rendered resource name or selector differs** from the live one
  (Helm release name, namespace), so adoption recreates or fails on an
  immutable field. A3 diffs the kustomize render against the old Helm
  render before merge.
- **The first hub sync of cert-manager wedges** on a deleted hook Job
  (`startupapicheck`), as on prod. `argocd app terminate-op` then a manual
  sync; documented in the checks runbook.
- **The hub controller's memory** grows with dev's resources cached;
  check cp1 before and after registering.
- **A sealed Vault looks healthy.** Apps go `Unknown`, health stays
  `Healthy`. `vault status` is the first check.
- **Prod is the only deploy path for dev.** The roadmap accepted this.
- **Misplaced ApplicationSet template keys are ignored silently**;
  `check-manifests.sh` stays strict.
- **`/etc/hosts`** on the owner's workstation still maps
  `prometheus.mgryn.cc` to dev until A4 retires dev's Prometheus ingress.

## Out of scope

- A kind-based CI cluster, Molecule role tests and `conftest` policies;
  considered and deferred. Molecule stays on its own track.
- Talos for dev.
- Deploying jobboard to prod and moving `jobs.mgryn.cc` (sub-5).
- Kargo, Image Updater, off-site backups.
